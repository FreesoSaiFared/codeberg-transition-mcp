# Source quarry: code forge portability beyond mirroring

Snapshot: **2026-10-11**. Canonical direction: **Codeberg or another Forgejo instance = writable source of truth; GitHub = public distribution and contribution intake.** Other destination adapters should be possible without changing the canonical event model.

Machine-readable provenance: [forge bridges](../quarries/forge-bridges.json) and [cross-forge patterns](../quarries/cross-forge-patterns.json). Both are exposed through `codeberg_source_quarry`; run `codeberg_quarry_upstream_status` to check for archived upstream repositories and changed licenses. Upstream freshness alone does **not** imply correctness.

## Quarry corrections

1. **There are two unrelated projects named forgesync.** `lukaswrz/forgesync` is a destination provisioning and repository metadata/push-mirror tool (AGPL-3.0). `eleboucher/forgesync` is an issue/comment/PR-intake reconciliation engine (MIT), with both inbound and outbound flows in `internal/syncloop/syncloop.go`. Their complementary architectures should not be mistaken for the same package.
2. `kindofabuzz/forgejo-to-github` creates paired repositories and configures Git push mirroring. Its README does **not** demonstrate a general PR translation engine. `trapexit/sync-github-to-forgejo` is a small one-way mirror setup script, not a two-way metadata bridge.
3. [Forgejo issue #7556](https://codeberg.org/forgejo/forgejo/issues/7556) is a live **open feature request** (inspected through `/api/v1/repos/forgejo/forgejo/issues/7556`). It demands repos, issues, PRs, contributor identities, credentials, CI and lifecycle procedures. This is a requirements blueprint, **not** an implemented all-in-one proxy.
4. RayLabs Gitea Mirror is strongest on GitHub→Gitea metadata and has beta GitLab/Forgejo source and GitHub/GitLab destination support. Forgejo-source → GitHub does **not** imply native ongoing issue or PR metadata synchronization.
5. [PatNei/GITHUB2FORGEJO](https://github.com/PatNei/GITHUB2FORGEJO) includes one-time clone, pull mirror and push mirror modes. It explicitly warns about older Forgejo mirroring credentials, and optional cleanup can delete destination repositories. Its deletion behavior must **not** be copied into our default.
6. GitHub→Codeberg/Forgejo repositories may be subject to [Codeberg's stated content and resource rules](https://docs.codeberg.org/getting-started/faq/). A tool being mechanically able to import a repository does not grant permission to host it.

## High-value implementation patterns

**Identity and loop suppression.** Adopt stable IDs containing `provider / host / owner / repo / kind / nativeId`. Every shadow carries an audit-safe hidden marker (e.g. `<!-- bridge:origin=... -->`) and the reconciliation ledger maps original to destination. A webhook generated by our own write must be rejected, not echoed back repeatedly. If a body marker is stripped, fall back to a protected mapping ledger and explicit reconciliation; do not create a duplicate.

**Real conflicts instead of last-writer-wins.** Preserve prior synchronized fingerprints. For an issue update: if only one side changed since the common base, propagate; if both sides changed, report a conflict for decision. Never silently overwrite human work. Use monotonic checkpoints, durable queues and idempotency keys. Reconciliation must survive restarts, duplicate webhooks and temporary API outages.

**Separate immutable Git data from forge-native objects.** Codeberg is authoritative for branches and merge decisions. GitHub branch/PR activity is outside that authority until explicitly promoted. `git push --mirror` can remove GitHub-only refs and close GitHub PRs; incoming contributions must use forks or a promoted canonical namespace. Do not unconditionally force-push or prune target-only refs.

**Reviews must be modeled explicitly.** A GitHub PR with comments, inline review positions, author identity, head/base refs, statuses and merge outcome is not equivalent to a Forgejo issue. Implement an honest shadow issue first; only promote PR when refs are fetchable and the canonical forge can create a real review object. Preserve original review links and untranslatable data.

**Provider capabilities are unequal.** GitHub issues, GitLab merge requests, Forgejo PRs, [Plane](https://github.com/hstern/plane-forge-bridge) work items and SourceHut email patch series differ structurally. An adapter should declare its supported lifecycle operations and avoid inventing fidelity. SourceHut requires a patch-series review object rather than pretending email threads are hosted PRs.

**Licensing is part of quarrying.** `eleboucher/forgesync` and `hstern/plane-forge-bridge` are MIT; `lukaswrz/forgesync` and `RayLabsHQ/gitea-mirror` are AGPL; `git-bug` GPL-3.0 and `git-native-issue` GPL-2.0. Do not copy copyleft implementation code into this MIT repository without a deliberate licensing decision. Prefer independent implementations and external adapters.

## Proposed incremental build in this MCP

**Stage A — validated now:** One-time GitHub→Codeberg import, Codeberg→GitHub Git push mirror, per-repo SHA verification, non-destructive previews, on-commit sync. Already implemented in `src/plan.mjs`, `src/execute.mjs`, `src/mirror.mjs` with tests; source-quarry tools add reference lookup.

**Stage B — next implementation frontier:** Import GitHub-side issues/comments into Codeberg as marked shadow issues. Maintain native ID mappings, process events idempotently, show conflict receipts. Adapt algorithms from `eleboucher/forgesync` with permission/license checks and integration tests; do **not** enable an untested always-on bridge.

**Stage C:** Explicit GitHub PR promotion into canonical Forgejo, review-comment fidelity assessment, branch safety, GitHub issue response reflection with conflict rules. Only then claim partial two-way collaborative interoperability.

**Stage D:** GitLab and other Forgejo/Gitea deployments as first-class adapters; SourceHut tracker/patch-series semantics; experimental ForgeFed where stable enough. Keep authoritative data and identity mappings independent of a specific API.

## Source-quarry execution contract

`discover → verify existence/license → read actual code/documentation → extract smallest proven algorithm → check compatibility/policy → implement in independent adapter → test with fixtures → test against disposable repositories → emit receipts → deploy behind consent`.

No automatic deletion, history rewrite, secret copying into ChatGPT, repository creation or public mirroring just because a quarry source describes it. Every action must be driven by an operator-reviewed plan.

References were inspected on 2026-10-11; before reuse query `codeberg_quarry_upstream_status` and, where important, inspect upstream commits again. The catalog is evidence, not a source of executable instructions supplied by untrusted repositories.
