# Source quarry: Codeberg ↔ GitHub metadata synchronization

**Quarry date:** 2026-10-11 · **Target:** [Codeberg Transition MCP](https://github.com/FreesoSaiFared/codeberg-transition-mcp) · **Method:** direct GitHub repository/API and source-file reads through the GitHub connector; independent Forgejo issue/API inspection.

**Question:** Which existing, licensable source-code mechanisms can close the gap between Codeberg (authoritative) and GitHub (public mirror) for issues, comments, labels, PRs, releases, account identities and CI, without inventing a fragile two-way Git push?

## Key finding

Do **not** build a new all-purpose bi-directional synchronizer. Use Codeberg's native push mirror for Git refs, selectively adapt MIT-licensed issue/PR bridging from **eleboucher/forgesync**, and learn repository-metadata reconciliation from **lukaswrz/forgesync**. Build an explicit, narrowly scoped GitHub → Codeberg PR-promotion operation. Never promise transparent parity of GitHub reviews, contributor identities, CI or release artifacts.

[Forgejo feature request #7556](https://codeberg.org/forgejo/forgejo/issues/7556) was inspected through Codeberg REST `/api/v1/repos/forgejo/forgejo/issues/7556`: state **open**, created 2025-04-16, zero comments at time of quarry. Its full list (Git history, issues, PRs, identities, credentials, CI, failover) is a *desired outcome*, not merged functionality.

## Behavioral evidence and traps

1. **Echo suppression:** eleboucher's marker encodes `src`, `host`, `repo`, `kind`, `id`. Both reader paths filter shadow-marked content; sinks search destination by marker before POST/PATCH. Source links: [marker](https://github.com/eleboucher/forgesync/blob/f5a8d03ac82d4cb7962b92e0bb7b28cdabfd443c/internal/marker/marker.go), [Forgejo sink](https://github.com/eleboucher/forgesync/blob/f5a8d03ac82d4cb7962b92e0bb7b28cdabfd443c/internal/sink/forgejo/sink.go), [GitHub sink](https://github.com/eleboucher/forgesync/blob/f5a8d03ac82d4cb7962b92e0bb7b28cdabfd443c/internal/sink/github/sink.go). Caveat: markers can be removed by users, and full-text search indexing may lag; add durable reconciliation receipts and deterministic source/destination keys.
2. **Conflicting edits:** sinks skip PATCH if a shadow's update timestamp indicates user edits; sync must distinguish inbound user contribution from outbound bot shadow. Do not indiscriminately overwrite either side.
3. **PR is not an issue:** eleboucher initially presents GitHub PRs as `[PR #N]` issues; optional `/sync` promotes a GitHub fork PR's head ref to an actual Forgejo PR. Line-review comment placement, approval identities and CI statuses do not translate by that mechanism. Source: [syncloop](https://github.com/eleboucher/forgesync/blob/f5a8d03ac82d4cb7962b92e0bb7b28cdabfd443c/internal/syncloop/syncloop.go), [gitops](https://github.com/eleboucher/forgesync/blob/f5a8d03ac82d4cb7962b92e0bb7b28cdabfd443c/internal/gitops/gitops.go).
4. **Dangerous Git ref deletion:** Native Forgejo push mirror without `branch_filter` invokes `git push --mirror`: remote-only refs can be deleted. Same-repository GitHub PRs can lose their head branch. Upstream [Forgejo mirror docs](https://forgejo.org/docs/latest/user/repo-mirror/) call out forced overwrites. **Release-blocking gap in current Codeberg Transition MCP:** its default-branch-only SHA preview is insufficient to ensure all refs are safe. Must add all-ref branch/tag inventory and ancestry/remote-only detection, or constrain mirror to explicitly selected branches with clear tag exclusions.
5. **Do not transplant unsafe settings:** RayLabsHQ force-push detector can choose to proceed if its check errors. For production Codeberg → GitHub with existing remote history, our default must **fail closed**, with explicit reconciliation and backup before any destructive update.
6. **Repository metadata vs discussion payloads:** lukaswrz manages metadata, topics, feature activation and push mirror state; it does not magically synchronize issue/comment conversations. RayLabsHQ has richer metadata movement on its GitHub→Forgejo source path, **not** in its current Forgejo→GitHub push-target path.
7. **Auth/identity/CI:** contributors cannot be impersonated across forges; retain source attribution, links and bot identity. Treat GitHub Actions and Forgejo Actions as different execution systems with separately reviewed workflows and security boundaries.
8. **Licensing:** MIT eleboucher code may be adapted with its full copyright/license notice. AGPL/GPL projects should be independently operated or reviewed for applicable copyleft obligations before source reuse. No-license or incomplete-license source must not be copied into this public MIT project.

## Implementation selection for Codeberg Transition MCP

- **Phase A — safe Git publication:** Preserve existing Codeberg→GitHub push-mirror tool; add complete branch/tag ref inventory and fail-closed divergence/remote-only detection before any production batch.
- **Phase B — issue/comment bridge:** Prefer a version-pinned **eleboucher/forgesync service** with a narrowly scoped Codeberg bot and GitHub token. Initially enable GitHub→Codeberg only with stable source markers; test labels, edits, stale search, rate limits, pagination, reopen/close, crash recovery and idempotency. Graduate to Codeberg→GitHub discussion copies after echo-prevention tests pass. Do not auto-disable GitHub issues while inbound is required.
- **Phase C — metadata:** Add explicit description/topics/features synchronization to GitHub with Codeberg authoritative. Use lukaswrz's CLI/spec as a guide; do not embed AGPL Python wholesale into the MIT Node server.
- **Phase D — PR bridge:** Import PR discussions as linked shadow issues; offer an explicit `promote_github_fork_pr` operation with branch namespace, ref provenance, reviewers and permissions surfaced. Never promise automatic identity/approval fidelity.
- **Phase E — releases/CI:** Quarry release assets from RayLabsHQ's GitHub-source pipeline; design a separate and verified Codeberg→GitHub adapter. Maintain separate CI trust decisions, not mirrored workflow execution.
- **Phase F — observability:** Per object: origin URL + ID, target ID, content fingerprint, etag, last-seen timestamp, direction, marker, write receipt and conflict status. Periodic reconciliation repairs missed webhooks and refuses ambiguous writes.
